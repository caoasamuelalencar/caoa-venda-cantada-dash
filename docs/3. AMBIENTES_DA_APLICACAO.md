## 3.1. Objetivo

Esta seção documenta os ambientes de desenvolvimento, homologação e produção do CAOA Venda Cantada Dash. Também define os procedimentos operacionais necessários para implantação, suporte, monitoramento, backup, recuperação e evolução para Azure.

Esta página complementa:

- **Seção 2 — Arquitetura da Solução:** componentes, integrações, segurança e arquitetura-alvo Azure.
- **Seção 4 — Gestão do Desenvolvimento e Entregas:** branches, Pull Requests, versionamento, aprovações, releases e governança de entrega.

> **Importante:** esta documentação diferencia o ambiente atualmente operado da arquitetura Azure planejada. Recursos Azure descritos como planejados não devem ser considerados provisionados sem inventário e evidência de aprovação.

---

## 3.2. Visão geral dos ambientes

O projeto possui três ambientes lógicos:

- **Desenvolvimento (DEV):** implementação, depuração e testes locais.
- **Homologação (HML):** validação técnica e funcional antes da publicação.
- **Produção (PRD):** operação corporativa da aplicação.

::: mermaid
graph LR;
    DEV[Desenvolvimento] --> HML[Homologacao];
    HML --> AP{Aprovacao};
    AP --> PRD[Producao];
    AP --> DEV;
:::

Todos os ambientes devem possuir configurações, credenciais e dados segregados. Não é permitido reutilizar segredos ou banco de produção em desenvolvimento ou homologação.

---

## 3.3. Desenvolvimento

### 3.3.1. Finalidade

O ambiente de desenvolvimento é utilizado para implementação de funcionalidades, correções, testes locais e depuração.

### 3.3.2. Configuração documentada

- Frontend Next.js: `http://localhost:3000`.
- Backend Express: `http://localhost:4000`.
- Banco lógico permitido: `salesdb_hml`.
- Arquivos de ambiente: `frontend/.env.development` e `backend/.env.development`.
- Execução principal:

```bash
pnpm install
pnpm dev:backend
pnpm dev
```

### 3.3.3. Regras de uso

- Não utilizar credenciais de produção.
- Não executar migrations destrutivas sem revisar o banco de destino.
- Não usar dados produtivos sem autorização e tratamento adequado.
- Executar lint, typecheck e testes relevantes antes de abrir Pull Request.

---

## 3.4. Homologação

### 3.4.1. Finalidade

Homologação valida tecnicamente e funcionalmente as mudanças antes da promoção para produção.

Atividades esperadas:

- testes integrados;
- validação dos critérios de aceite;
- execução de smoke tests;
- registro de evidências;
- abertura e revalidação de bugs;
- aprovação, reprovação ou bloqueio da entrega.

### 3.4.2. Configuração atual

O ambiente de homologação atualmente utiliza deploy nativo em VM Windows por Azure Pipelines.

- Environment do Azure DevOps: `homolog`.
- Pool do agente: `VendaCantada-Homolog`.
- Grupo de variáveis: `vg-venda-cantada-homolog`.
- Branches previstas pelo YAML: `develop` e `test/deploy-homolog`.
- Diretório de publicação: `C:\projetos\VendaCantadaHml\current`.
- Arquivo de ambiente: `D:\Apps\VendaCantadaHml\config\.env.homolog`.
- Log da aplicação: `D:\Apps\VendaCantadaHml\logs\application.log`.
- Tarefa agendada: `CAOA Venda Cantada - Homolog`.
- Frontend local da VM: porta `3003`.
- Backend local da VM: porta `4000`.
- Banco lógico permitido: `salesdb_hml`.

### 3.4.3. Fluxo atual de homologação

::: mermaid
graph LR;
    REPO[Azure Repos] --> CI[CI Linux];
    CI --> DEPLOY[Deploy na VM HML];
    DEPLOY --> ENV[Arquivo .env.homolog protegido];
    DEPLOY --> CODE[Codigo em C drive];
    CODE --> TASK[Tarefa agendada Windows];
    TASK --> FE[Frontend porta 3003];
    TASK --> API[Backend porta 4000];
    API --> DB[SQL Server salesdb_hml];
    FE --> HEALTH[Health checks];
    API --> HEALTH;
:::

### 3.4.4. Segregação obrigatória

- Utilizar `APP_ENV=homolog`.
- Aceitar somente `salesdb_hml` como banco de HML.
- Manter `.env.homolog` fora do diretório publicado.
- Restringir o arquivo de ambiente à conta de execução e administradores autorizados.
- Não usar segredos, certificados ou banco de produção.
- Registrar a versão, o build e a evidência de homologação antes de aprovar a promoção.

## 3.5. Produção

### 3.5.1. Finalidade

Produção atende as operações corporativas e utiliza dados reais. Qualquer alteração deve ser rastreável, aprovada e reversível conforme o plano de recuperação.

### 3.5.2. Topologias suportadas pelo repositório

O repositório suporta os seguintes cenários de produção:

- Docker com Nginx como proxy HTTPS;
- execução nativa com Next.js e backend Node.js;
- IIS como proxy reverso no cenário Windows;
- PM2 como gerenciador de processos, quando adotado.

::: mermaid
graph LR;
    U[Usuario] --> N[Nginx ou IIS HTTPS];
    N --> FE[Frontend Next.js];
    FE --> API[Backend Express];
    API --> DB[SQL Server salesdb];
:::

### 3.5.3. Requisitos mínimos de produção

- `APP_ENV=production`.
- Banco lógico permitido: `salesdb`.
- DNS e certificado TLS válidos.
- Segredos fora do código-fonte.
- Backup recuperável e recuperação testada.
- Health checks e logs disponíveis.
- Processo de aprovação para alterações e releases.
- Procedimento de rollback documentado.

### 3.5.4. Registro obrigatório da topologia efetiva

Antes da entrada em produção, registrar nesta seção:

- host, VM ou serviço de hospedagem;
- DNS público ou corporativo;
- responsável técnico e operacional;
- local de logs;
- versão publicada;
- banco de produção;
- certificado TLS;
- política de backup;
- última data de teste de restauração;
- evidência de aprovação de produção.

## 3.6. Configuração e segregação entre ambientes

### 3.6.1. Dados

- Desenvolvimento e homologação usam o banco lógico `salesdb_hml`.
- Produção usa o banco lógico `salesdb`.
- O uso do mesmo nome lógico em DEV e HML não comprova instância, servidor ou infraestrutura física compartilhada.
- O isolamento efetivo deve ser confirmado por host, porta, credenciais, rede e permissões.

### 3.6.2. Credenciais e segredos

- Cada ambiente deve possuir valores próprios para banco, autenticação, URLs e certificados.
- Credenciais não podem ser registradas em código, commits, Work Items, logs ou Wiki.
- Variáveis protegidas devem ser mantidas em Variable Groups, Key Vault ou solução corporativa equivalente.
- O acesso deve seguir privilégio mínimo.

### 3.6.3. Aplicação e publicação

- O build de desenvolvimento não deve ser reutilizado como release produtiva sem validação.
- Homologação deve receber versão identificável por commit e build.
- Produção deve receber versão previamente homologada e aprovada.
- Configuração, código, banco e segredos devem poder ser auditados por ambiente.

## 3.7. Pipeline de integração e deploy

### 3.7.1. Integração contínua atual

O pipeline `azure-pipelines.yml` executa:

1. instalação de Node.js 24 e pnpm 11.1.3;
2. instalação congelada de dependências;
3. geração do Prisma Client;
4. lint;
5. validação TypeScript de frontend e backend;
6. build de frontend e backend.

### 3.7.2. Deploy de homologação atual

Após a CI bem-sucedida, o deploy de HML:

1. valida as variáveis obrigatórias;
2. valida que `DATABASE_URL` aponta para `salesdb_hml`;
3. cria o arquivo `.env.homolog` protegido;
4. para a tarefa agendada existente;
5. publica o código na VM;
6. instala dependências, gera Prisma Client e executa build;
7. inicia a tarefa `CAOA Venda Cantada - Homolog`;
8. valida backend em `/health`;
9. valida o frontend na porta `3003`.

### 3.7.3. Check de branches do Environment

O YAML permite deploy de homologação a partir das branches:

```text
refs/heads/develop
refs/heads/test/deploy-homolog
```

O check **Branch control** do Environment `homolog` deve permitir essas mesmas referências totalmente qualificadas:

```text
refs/heads/develop,refs/heads/test/deploy-homolog
```

As branches devem permanecer protegidas. Quando a branch temporária deixar de ser usada, ela deve ser removida simultaneamente do YAML e do check do Environment.

### 3.7.4. Limitações atuais

- O Azure Pipeline não executa testes unitários e E2E.
- O pipeline não publica artefatos imutáveis.
- O pipeline não publica imagens em Azure Container Registry.
- O pipeline não aplica infraestrutura como código.
- O pipeline não faz deploy automatizado para produção.

### 3.7.5. Pipeline de produção preparada e desativada

O `azure-pipelines.yml` possui o estágio `DeployProduction`, disponível apenas
para a branch `main`. A publicação na VM é controlada pelo parâmetro booleano
`publishProduction`, cujo padrão é `false`. Portanto, pushes e execuções
manuais com o valor padrão não acessam o Environment, o pool, as variáveis, a
VM nem o banco de produção; o job apenas registra que a publicação não foi
executada.

Quando a publicação for formalmente autorizada, execute manualmente a pipeline
em `main` com `publishProduction=true`. Antes disso, a equipe DevOps deve
configurar os checks e aprovadores no Environment `production`, autorizar o
pool `VendaCantada-Producao` e criar o Variable Group protegido
`vg-venda-cantada-producao` com os segredos e as seguintes variáveis
operacionais:

- `PRODUCTION_CONFIGURATION_DIRECTORY`: diretório externo ao código para o
  arquivo `.env.production`;
- `PRODUCTION_TARGET_DIRECTORY`: diretório exclusivo que receberá a publicação
  via `robocopy /MIR`;
- `PRODUCTION_TASK_NAME`: tarefa agendada que inicia a aplicação.

O job valida que o banco seja `salesdb`, escreve a configuração protegida,
publica o código, gera o build, reinicia a tarefa e executa health checks. Como
o `robocopy /MIR` pode remover arquivos no diretório de destino, a pasta deve
ser exclusiva da aplicação. A habilitação exige aprovação da janela de mudança,
validação de backup/migration e um plano de rollback.

## 3.8. Migrations e mudanças de banco

### 3.8.1. Regras

- Toda alteração de schema deve atualizar `backend/prisma/schema.prisma`.
- Toda alteração persistente deve criar migration em `backend/prisma/migrations/`.
- Migrations devem ser testadas primeiro em DEV e HML.
- Seeds destrutivos de desenvolvimento não podem ser executados em produção.
- O Pull Request ou Work Item deve registrar impacto, risco e plano de recuperação.

### 3.8.2. Homologação

A tarefa agendada de HML executa a aplicação pelo comando `pnpm start:homolog`. Durante a inicialização, o backend executa `prisma migrate deploy` antes de iniciar a API.

Antes de aprovar o deploy, confirmar:

1. banco de destino igual a `salesdb_hml`;
2. migration revisada;
3. ausência de seed destrutivo;
4. plano de rollback disponível;
5. backup ou cópia recuperável, quando a mudança for destrutiva;
6. health checks concluídos após a publicação.

### 3.8.3. Produção

Enquanto não houver pipeline produtiva aprovada, migration em produção deve ocorrer somente em janela autorizada, com responsável de banco e evidência registrada.

O procedimento mínimo é:

1. aprovar a mudança e a janela;
2. confirmar backup recuperável;
3. registrar versão e migration alvo;
4. executar migration de forma explícita e auditável;
5. executar smoke tests;
6. monitorar a aplicação e o banco;
7. registrar o resultado.

## 3.9. Rollback e recuperação de versão

### 3.9.1. Quando iniciar rollback

- indisponibilidade após publicação;
- falha crítica de autenticação;
- erros generalizados da API;
- falha em fluxo essencial;
- migration com impacto não previsto;
- incidente de segurança relacionado à release.

### 3.9.2. Rollback de aplicação em HML

1. Registrar o incidente e suspender novos deploys.
2. Identificar o último commit ou release estável.
3. Confirmar compatibilidade do banco com a versão anterior.
4. Publicar a versão estável pelo pipeline ou procedimento aprovado.
5. Reiniciar a tarefa agendada de HML.
6. Executar health checks e fluxos críticos.
7. Registrar evidências e causa-raiz.

> O deploy atual usa `robocopy /MIR` e não mantém artefatos imutáveis. A recuperação depende de commit conhecido e publicação controlada. A evolução recomendada é promover artefatos ou imagens imutáveis.

### 3.9.3. Rollback de banco

Rollback de aplicação não reverte automaticamente alterações de dados ou schema.

- Não reverter migrations sem avaliação do responsável pelo banco.
- Preferir migrations compatíveis em duas etapas para mudanças de alto risco.
- Recuperar banco somente com aprovação explícita e backup validado.
- Registrar decisão, dados afetados e evidências da recuperação.

## 3.10. Monitoramento, alertas e suporte

### 3.10.1. Monitoramento atual

- Health check do backend em `/health`.
- Health checks executados pela pipeline após deploy em HML.
- Log de HML em `D:\Apps\VendaCantadaHml\logs\application.log`.
- Swagger e OpenAPI para diagnóstico de contrato de API.

### 3.10.2. Alertas mínimos esperados para produção

- indisponibilidade de frontend ou backend;
- falha no endpoint de saúde;
- aumento de erros HTTP 5xx;
- aumento de latência da API;
- falha de conexão com banco;
- falha de deploy ou migration;
- expiração de certificado ou segredo;
- consumo de quota que ameace disponibilidade.

### 3.10.3. Atendimento inicial de incidente

1. Registrar data, hora, ambiente, versão e sintoma.
2. Verificar health checks e logs.
3. Identificar o último deploy, migration ou alteração de configuração.
4. Avaliar impacto para usuários e dados.
5. Acionar o responsável técnico conforme severidade.
6. Decidir entre correção, contenção ou rollback.
7. Registrar causa-raiz, evidências e ação preventiva.

## 3.11. Backup, restauração e recuperação de dados

### 3.11.1. Scripts existentes

O repositório possui os scripts:

- `scripts/sql/clone-salesdb-to-salesdb-hml.sql`;
- `scripts/sql/verify-salesdb-hml-clone.sql`.

Eles usam backup `COPY_ONLY`, `RESTORE VERIFYONLY` e recriam `salesdb_hml` a partir de `salesdb`.

> Esses scripts são destinados à renovação controlada de homologação. Eles não substituem backup, retenção e recuperação de produção.

### 3.11.2. Regras para cópia de dados em HML

1. Confirmar autorização para cópia de dados.
2. Avaliar anonimização de dados pessoais.
3. Confirmar que o destino é `salesdb_hml`.
4. Executar o script de verificação após a restauração.
5. Registrar responsável, data e resultado.

### 3.11.3. Requisitos de produção

Antes de produção, registrar:

- política de backup;
- retenção;
- ponto de recuperação;
- estratégia de geo-restore, quando aplicável;
- RPO e RTO aprovados;
- responsável pela recuperação;
- frequência de testes;
- evidência da última restauração bem-sucedida.

### 3.11.4. Procedimento de recuperação

1. Declarar incidente e suspender operações que agravem perda de dados.
2. Identificar o ponto de recuperação aprovado.
3. Restaurar em destino isolado quando possível.
4. Validar integridade, permissões, migrations e fluxos críticos.
5. Obter autorização do responsável pelo banco e do negócio antes da troca de destino.
6. Registrar tempo total, dados recuperados, perdas conhecidas e evidências.

## 3.12. Evolução para Microsoft Azure

### 3.12.1. Arquitetura-alvo

::: mermaid
graph LR;
    U[Usuario corporativo] --> WAF[Camada WAF aprovada];
    WAF --> FE[Azure Container Apps Frontend];
    FE --> API[Azure Container Apps Backend interno];
    API --> DB[Azure SQL Database];
    PIPE[Azure DevOps Pipelines] --> ACR[Azure Container Registry];
    ACR --> FE;
    ACR --> API;
    FE --> KV[Azure Key Vault];
    API --> KV;
    FE --> AI[Application Insights];
    API --> AI;
    AI --> LAW[Log Analytics];
:::

### 3.12.2. Recursos previstos

- Azure Container Apps para frontend e backend;
- Azure Container Registry;
- Azure SQL Database ou Azure SQL Managed Instance;
- Azure Key Vault;
- Managed Identities;
- VNet, sub-redes, Private Endpoints e Private DNS Zones;
- Application Gateway WAF v2 ou equivalente corporativo;
- Application Insights, Log Analytics e Azure Monitor;
- infraestrutura como código em Bicep;
- service connections e Environments protegidos no Azure DevOps.

### 3.12.3. Inventário obrigatório após provisionamento

Para cada recurso Azure, registrar:

- nome;
- tipo;
- subscription;
- Resource Group;
- região;
- SKU ou plano;
- resource ID;
- ambiente;
- proprietário técnico;
- proprietário de negócio;
- classificação de dados;
- endpoint ou DNS, quando aplicável;
- dependências;
- data de criação e última revisão.

### 3.12.4. Status da evolução

A arquitetura Azure permanece **proposta** até que os recursos estejam provisionados, inventariados, testados e aprovados pelas áreas responsáveis.
