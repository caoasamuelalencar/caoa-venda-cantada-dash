## 6.1. Objetivo

Esta seção documenta as interfaces HTTP da solução, a comunicação entre frontend, BFF e backend, além das integrações com Microsoft Entra ID, Microsoft Graph e SQL Server.

Objetivos:

- identificar consumidores, provedores, contratos e responsabilidades;
- registrar autenticação, autorização, timeouts e tratamento de falhas;
- descrever os dados trafegados e os cuidados de segurança;
- indicar a documentação executável disponível em OpenAPI;
- estabelecer regras para evoluir contratos sem quebra de consumidores.

> **Escopo:** interfaces usadas pela aplicação. Não há, no código atual, uma API pública destinada a terceiros ou parceiros externos.

---

## 6.2. Visão geral das integrações

O navegador consome as rotas BFF do Next.js em `/api`. O BFF valida a sessão corporativa, cria uma identidade assinada de curta duração e a encaminha à API Express. A API aplica as permissões e acessa o SQL Server.

::: mermaid
graph LR;
    U[Usuario] --> FE[Frontend Next.js];
    FE --> BFF[Rotas BFF /api];
    BFF --> AUTH[NextAuth e Microsoft Entra ID];
    BFF --> API[API Express interna];
    API --> SQL[SQL Server];
    AUTH --> GRAPH[Microsoft Graph];
    API --> DOCS[OpenAPI e Swagger];
:::

Fluxo principal:

`Navegador → BFF Next.js → API Express → SQL Server`

---

## 6.3. Componentes e responsabilidades

### 6.3.1. Frontend Next.js

- exibe as páginas e componentes da aplicação;
- usa as rotas BFF para operações de negócio;
- não deve conhecer nem expor a URL interna do backend;
- mantém a sessão do usuário por meio do NextAuth;
- apresenta estados de carregamento, sucesso e erro ao usuário.

### 6.3.2. BFF — Backend for Frontend

- recebe requisições do navegador em `/api`;
- recupera a sessão válida do NextAuth;
- remove headers sensíveis recebidos do navegador;
- assina uma identidade de curta duração para o backend;
- encaminha método, query string e corpo da requisição;
- aplica timeout de backend e tenta URLs configuradas de fallback;
- devolve a resposta do backend ao frontend.

### 6.3.3. API Express

- expõe os endpoints internos de negócio;
- valida a assinatura e expiração da identidade encaminhada pelo BFF;
- sincroniza o usuário autenticado com a tabela `User`;
- aplica autorização por perfil, permissão ou administração;
- valida dados, executa regras de negócio e persiste informações;
- disponibiliza health check e contrato OpenAPI.

### 6.3.4. SQL Server

- persiste intenções de venda, fluxo de loja, usuários, perfis, permissões e telas;
- fornece catálogos comerciais e de veículos;
- é acessado pelo Prisma e por consultas SQL controladas para objetos de catálogo.

## 6.4. Interfaces HTTP internas

### 6.4.1. API Express

As rotas abaixo pertencem ao backend. Elas não devem ser chamadas diretamente pelo navegador em ambientes corporativos; o acesso deve ocorrer por meio do BFF.

Endpoints técnicos sem autenticação de negócio:

- `GET /health`: verifica a disponibilidade da API e responde `{ "status": "ok" }`.
- `GET /docs`: apresenta a interface Swagger.
- `GET /openapi.json`: disponibiliza o contrato OpenAPI em JSON.

Todos os demais endpoints passam pelo middleware de autenticação do backend.

### 6.4.2. Rotas BFF públicas para o frontend

As rotas abaixo são a interface utilizada pelas telas do sistema. Elas ficam sob o prefixo `/api` no frontend.

- `/api/sales-intentions`
- `/api/sales-intentions/search`
- `/api/sales-intentions/latest-request-date`
- `/api/sales-intentions/{id}`
- `/api/sales-intention-catalogs`
- `/api/sales-intention-classificacoes`
- `/api/sales-intention-modelos-dealer`
- `/api/store-flows`
- `/api/users/*`
- `/api/perfil/acesso`
- `/api/perfil/foto`
- `/api/auth/[...nextauth]`

As rotas de perfil e autenticação são específicas do frontend e não possuem equivalente direto de negócio no backend.

## 6.5. Catálogo de endpoints de negócio

### 6.5.1. Intenções de venda

- `GET /sales-intentions`: lista intenções do mês corrente ou aplica filtros simples recebidos por query string.
- `GET /sales-intentions/search`: pesquisa intenções com filtros avançados.
- `GET /sales-intentions/latest-request-date`: retorna a data mais recente de solicitação, ou `null` quando não houver registros.
- `GET /sales-intentions/:id`: consulta uma intenção por identificador.
- `POST /sales-intentions`: cria uma intenção de venda.
- `PUT /sales-intentions/:id`: atualiza uma intenção existente.
- `DELETE /sales-intentions/:id`: exclui uma intenção existente.

Permissões exigidas:

- consulta: `INTENTION_VIEW`;
- criação: `INTENTION_CREATE`;
- alteração: `INTENTION_UPDATE`;
- exclusão: `INTENTION_DELETE`.

O payload de intenção inclui os campos comerciais e operacionais definidos no contrato `SalesIntentionCreateInput`, como proprietário, tipo de venda, bandeira, regional, loja, veículo, classificação, quantidade, data da solicitação, anos e placa.

### 6.5.2. Catálogos de intenção de venda

- `GET /sales-intention-catalogs`: retorna fontes, hierarquia de bandeira/regional/loja e combinações comerciais usadas no formulário.
- `GET /sales-intention-classificacoes`: retorna classificações usadas nos relatórios.
- `GET /sales-intention-modelos-dealer`: retorna combinações de tipo de venda, marca, modelo e versão.
- `GET /sales-intention-modelos-dealer/by-placa?placa={placa}`: procura dados de veículo pela placa.

Todos exigem a permissão `INTENTION_VIEW`.

Os catálogos são normalizados na API para reduzir duplicidades e diferenças de capitalização ou espaços. A consulta por placa remove hífens e espaços para realizar a busca.

### 6.5.3. Fluxo de loja

- `POST /store-flows`: cria ou atualiza o fluxo do dia para a combinação regional e loja.

Permissão exigida: `STORE_FLOW_CREATE`.

Payload esperado:

```json
{
  "regional": "CY1",
  "lojaVenda": "D21-0713-RIBEIRAO PRETO",
  "fluxo": 120
}
```

Regras de validação:

- `regional` e `lojaVenda` são obrigatórios;
- `fluxo` deve ser um número inteiro entre `1` e `1000000`;
- a gravação é um `upsert` para a data atual, regional e loja.

### 6.5.4. Usuários, perfis e telas

Rotas disponíveis para o usuário autenticado:

- `GET /users/me/access`: retorna perfis e telas liberadas para a sessão atual.
- `GET /users/me/screens`: retorna códigos de telas liberadas para a sessão atual.

Rotas administrativas, restritas ao perfil `ADMIN`:

- `GET /users/access-management/context`;
- `GET /users/access-management`;
- `GET /users`;
- `GET /users/roles`;
- `GET /users/screens`;
- `GET /users/:id/roles`;
- `PATCH /users/:id/status`;
- `DELETE /users/:id`;
- `PUT /users/:id/roles`;
- `PUT /users/:id/screens`.

Controles adicionais do módulo administrativo:

- um administrador não pode remover o próprio acesso administrativo;
- o último administrador ativo não pode ser desativado ou excluído;
- a exclusão de usuário preserva intenções históricas, removendo apenas o vínculo de criador quando necessário.

## 6.6. Autenticação e autorização

### 6.6.1. Autenticação do usuário

O frontend utiliza NextAuth com Microsoft Entra ID. O fluxo solicita os escopos:

- `openid`;
- `profile`;
- `email`;
- `offline_access`;
- `User.Read`.

O login exige nova autenticação no provedor por meio de `prompt=login` e `max_age=0`. O fallback de credenciais só é disponibilizado quando habilitado explicitamente pelas variáveis `NEXTAUTH_FALLBACK_AUTH` ou `NEXT_PUBLIC_FALLBACK_AUTH`; ele não deve ser utilizado em produção sem aprovação formal de Segurança.

### 6.6.2. Identidade entre BFF e backend

O BFF cria o header interno `x-caoa-authorization` com:

1. payload JSON codificado em Base64URL;
2. assinatura HMAC SHA-256 usando `BACKEND_AUTH_SECRET`;
3. expiração de cinco minutos.

O payload contém:

- `entraObjectId`;
- `tenantId`;
- `name`;
- `email`, quando disponível;
- `department` e `jobTitle`, quando disponíveis;
- `exp`, data de expiração em milissegundos.

O backend compara a assinatura de forma segura, valida os campos e sincroniza o usuário antes de autorizar a chamada.

> `BACKEND_AUTH_SECRET` deve ser exclusivo por ambiente e mantido em cofre seguro. Ele não pode ser exposto ao navegador, incluído em logs ou compartilhado em canais não aprovados.

### 6.6.3. Autorização

Após autenticar a identidade, a API carrega perfis, permissões e telas do usuário. A autorização é aplicada pela API e não apenas pela interface.

::: mermaid
sequenceDiagram
    participant FE as Frontend
    participant BFF as BFF
    participant API as API Express
    participant DB as SQL Server

    FE->>BFF: Requisicao para /api
    BFF->>BFF: Valida sessao NextAuth
    BFF->>API: Header x-caoa-authorization assinado
    API->>API: Valida HMAC e expiracao
    API->>DB: Sincroniza usuario e carrega permissoes
    DB-->>API: Contexto de autorizacao
    API-->>BFF: Resposta autorizada ou negada
    BFF-->>FE: Resposta HTTP
:::

## 6.7. Padrões de resposta, erros e timeout

### 6.7.1. Respostas de sucesso

- `200 OK`: consulta, alteração ou operação concluída.
- `201 Created`: criação de intenção ou registro de fluxo concluída.
- `204 No Content`: exclusão ou atualização sem corpo de resposta.

### 6.7.2. Respostas de erro

O backend responde, em regra, no formato:

```json
{
  "message": "Descrição do erro"
}
```

Status mais relevantes:

- `400 Bad Request`: identificador, query string ou payload inválido.
- `401 Unauthorized`: sessão ou identidade interna ausente, inválida ou expirada.
- `403 Forbidden`: perfil ou permissão insuficiente.
- `404 Not Found`: recurso inexistente.
- `500 Internal Server Error`: falha inesperada.
- `503 Service Unavailable`: indisponibilidade de backend ou esgotamento temporário do pool de conexões com o banco.

Quando o pool do Prisma expira, a API retorna `503` e o header `Retry-After: 3`.

### 6.7.3. Timeout e resiliência do BFF

O BFF utiliza timeout padrão de **30 segundos** por tentativa de chamada ao backend. O valor pode ser configurado por `BACKEND_REQUEST_TIMEOUT_MS`, desde que seja no mínimo um segundo.

As URLs candidatas de backend são obtidas, nesta ordem, de:

1. `API_BASE_URL`;
2. `NEXT_PUBLIC_API_BASE_URL`;
3. endereços de desenvolvimento ou contêiner definidos pelo código.

Em caso de erro de rede ou timeout, o BFF tenta a próxima URL candidata. Esse comportamento não substitui balanceamento de carga, health probes ou estratégia de alta disponibilidade.

## 6.8. Integração com Microsoft Entra ID

### 6.8.1. Finalidade

O Microsoft Entra ID é o provedor de identidade corporativa. Ele autentica o usuário e fornece claims necessárias para identificar a pessoa no sistema.

### 6.8.2. Dados consumidos

- ID do objeto do usuário (`oid`);
- ID do tenant (`tid`);
- nome;
- e-mail ou UPN;
- claims de diretório disponíveis no token.

Os identificadores `tenantId` e `entraObjectId` formam a chave de identidade persistida na aplicação.

### 6.8.3. Dependências de configuração

- `AZURE_AD_CLIENT_ID`;
- `AZURE_AD_CLIENT_SECRET`;
- `AZURE_AD_TENANT_ID`;
- `NEXTAUTH_URL`;
- `NEXTAUTH_SECRET`.

As URIs de callback e logout devem ser configuradas na App Registration para cada ambiente. Qualquer alteração exige validação de Segurança ou do time responsável pela identidade corporativa.

## 6.9. Integração com Microsoft Graph

### 6.9.1. Finalidade

Após o login, o frontend consulta o Microsoft Graph para enriquecer o perfil do usuário e obter sua foto quando disponível.

Chamadas identificadas no código:

- `GET https://graph.microsoft.com/v1.0/me` com seleção de atributos de perfil;
- `GET https://graph.microsoft.com/v1.0/me/photos/240x240/$value` para foto de perfil.

### 6.9.2. Dados de perfil

Os dados podem incluir nome, e-mail, cargo, departamento e outros atributos retornados pelo Graph e apresentados na página de perfil.

Tratamento de falha:

- se o token não estiver disponível, a integração retorna ausência de dados adicionais;
- se a chamada ao Graph falhar, o login continua com as claims disponíveis;
- a ausência de foto não deve bloquear o uso da aplicação.

### 6.9.3. Segurança e privacidade

- Solicitar apenas permissões Microsoft Graph necessárias, atualmente `User.Read` delegado.
- Não registrar access token, refresh token ou dados pessoais desnecessários em logs.
- Revisar periodicamente as permissões consentidas na App Registration.
- Validar a necessidade de exibir atributos pessoais antes de ampliar o escopo de leitura.

## 6.10. Integração com SQL Server e catálogos

### 6.10.1. Persistência de aplicação

O Prisma acessa as tabelas operacionais e de autorização descritas na [Seção 5 — Banco de dados](5.%20BANCO_DE_DADOS.md).

Principais operações:

- criação, consulta, alteração e exclusão de intenções de venda;
- criação ou atualização diária de fluxo de loja;
- sincronização do usuário autenticado;
- leitura e manutenção de perfis, permissões e telas;
- leitura de combinações válidas de formulário.

### 6.10.2. Catálogos consultados com SQL controlado

As seguintes estruturas são consultadas diretamente por repositórios específicos:

- `VW_IntencaoVendas_Empresa`;
- `VW_IntencaoVendas_ClassificacaoVenda`;
- `VW_IntencaoVendas_ModelosDealer`;
- `VW_IntencaoVendas_TipoVenda`.

Conforme documentado na Seção 5, o nome `VW_` não garante que o objeto físico seja uma view em todos os ambientes: em homologação, a estratégia atual pode usar tabelas locais sincronizadas com a origem.

### 6.10.3. Requisitos de disponibilidade

- A API depende de conectividade com SQL Server para executar operações de negócio.
- A indisponibilidade do banco impacta login na aplicação, permissões, catálogos e operações de cadastro.
- Consultas de catálogo possuem cache local de cinco minutos no processo da API.
- Consultas de intenções possuem cache local de dez segundos.
- Em múltiplas réplicas, esses caches não são compartilhados; qualquer mudança de estratégia deve considerar cache distribuído, se necessário.

## 6.11. OpenAPI, Swagger e gestão de contratos

O backend disponibiliza:

- `/openapi.json`: contrato OpenAPI 3.0.3;
- `/docs`: interface Swagger baseada no contrato.

O arquivo fonte é `backend/src/swagger.ts`.

### 6.11.1. Regra de evolução

Toda alteração em endpoint, método HTTP, parâmetro, payload, status de resposta ou regra de autorização deve incluir:

1. atualização da rota, controller, serviço e validador aplicáveis;
2. atualização dos tipos do frontend e do BFF;
3. atualização do OpenAPI;
4. testes unitários e de integração relevantes;
5. atualização desta Wiki, quando houver impacto de integração;
6. registro da quebra de compatibilidade em release notes, quando aplicável.

### 6.11.2. Lacunas atuais a tratar

O contrato OpenAPI já cobre os principais recursos de intenção, catálogos e administração, mas deve ser mantido em sincronia com todas as rotas implementadas. Em especial, revisar a cobertura de:

- `GET /sales-intentions/latest-request-date`;
- `POST /store-flows`;
- `PATCH /users/:id/status`.

Também é recomendado declarar no OpenAPI o mecanismo de autenticação interna, os status de erro padronizados e o servidor por ambiente, sem publicar URLs internas ou segredos.

## 6.12. Requisitos para novas integrações

Antes de criar uma nova API ou integrar um fornecedor externo, registrar no Work Item e nesta página:

- objetivo de negócio;
- sistema consumidor e sistema provedor;
- proprietário técnico e responsável de negócio;
- classificação dos dados trafegados;
- autenticação e autorização;
- endpoint, método e contrato;
- volume esperado, timeout e limite de requisições;
- estratégia de retentativa, idempotência e tratamento de duplicidade;
- monitoramento, alertas e logs necessários;
- plano para indisponibilidade do serviço dependente;
- critérios de aceite e testes de integração;
- política de versionamento e descontinuação do contrato.

Integrações externas não devem receber acesso direto ao banco de dados da aplicação.

## 6.13. Segurança das interfaces

- O backend deve permanecer em rede interna ou protegido por camada de entrada aprovada.
- O navegador deve usar exclusivamente o BFF para endpoints de negócio.
- O BFF remove headers `authorization` e `x-caoa-authorization` recebidos do cliente antes de gerar a identidade própria.
- Segredos devem ser separados por ambiente e mantidos fora do código.
- O CORS do backend deve ser revisado e restrito às origens necessárias antes de produção, caso o backend possa ser acessado fora da rede interna.
- Logs devem evitar payloads que contenham tokens, connection strings ou dados pessoais desnecessários.
- Endpoints de diagnóstico devem ser expostos somente conforme a política corporativa de rede e segurança.
- Toda integração externa deve usar TLS e validação de certificados.

## 6.14. Operação, monitoramento e suporte

Monitorar no mínimo:

- disponibilidade de `/health`;
- taxa de erros HTTP 4xx e 5xx;
- latência do BFF, API e consultas SQL;
- falhas de autenticação Entra ID;
- falhas de consulta ao Microsoft Graph;
- esgotamento do pool de conexões Prisma;
- timeout de comunicação entre BFF e backend;
- volume de respostas `503` e uso de `Retry-After`.

No atendimento de incidente:

1. registrar ambiente, horário, usuário afetado e endpoint;
2. verificar a saúde da API e o último deploy ou migration;
3. confirmar se a falha está no BFF, na API, na identidade, no Graph ou no banco;
4. consultar logs sem expor dados sensíveis;
5. aplicar contenção, correção ou rollback conforme os procedimentos da Seção 3;
6. registrar causa-raiz e ação preventiva.

## 6.15. Checklist de validação

- [ ] Rotas BFF e endpoints Express estão documentados e coerentes.
- [ ] Contrato OpenAPI reflete as rotas de produção.
- [ ] Autenticação Entra ID está validada em cada ambiente.
- [ ] `BACKEND_AUTH_SECRET` é exclusivo, protegido e rotacionável por ambiente.
- [ ] Permissões de Microsoft Graph seguem privilégio mínimo.
- [ ] CORS e exposição de backend foram revisados para produção.
- [ ] Timeouts, indisponibilidades e respostas `503` possuem monitoramento.
- [ ] Objetos de catálogo SQL estão identificados como views ou tabelas em cada ambiente.
- [ ] Novas integrações possuem responsável, contrato, monitoramento e plano de contingência.
- [ ] Documentação foi revisada por Desenvolvimento, Arquitetura, Segurança e responsáveis pelas integrações.
